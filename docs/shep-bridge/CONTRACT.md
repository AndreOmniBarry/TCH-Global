# TCH website ⇄ SHEP.HRD bridge — wire contract v1 (signed off by security review)

Both sides MUST implement exactly this. Any change bumps the version.

## 1. Website → SHEP: POST {SHEP}/api/bridge/ingest
Headers
- Content-Type: application/json   (body ≤ 16 KB, else 413)
- X-Bridge-Key: <keyId>            e.g. tch-k1
- X-Bridge-Timestamp: <unix seconds, integer, digits only>
- X-Bridge-Signature: v1=<hex HMAC-SHA256(secret, canonical)>

canonical = join("\n", [ "v1", "POST", "/api/bridge/ingest", <host>, <ts>, <keyId>, <hex sha256(rawBody)> ])
- <host> = lowercase host of the SHEP base URL (no scheme, no port unless non-default).
  SHEP compares against env BRIDGE_EXPECTED_HOST (never trusts the request Host header).
- Verify: |now - ts| ≤ 300 s; decode hex, equal length, crypto.timingSafeEqual.
  Unknown keyId → still compute an HMAC with a dummy key, then 401.
- Website re-signs every attempt; signatures are never stored.

Body (envelope)
{ "v": 1, "id": "<uuid v4, generated by website server>", "type": "<type>",
  "occurredAt": "<ISO-8601>", "consent": { "version": "2026-10", "at": "<ISO-8601>" },
  "data": { ...per type, strict, unknown keys → 422 } }

Types (strings are trimmed, control chars stripped, newline allowed only in note/request/team_idea)
- member.join          { full_name 2-120, email? ≤160, phone? ≤32, note? ≤1000 }   (email or phone required)
- care.salvation       { full_name 2-120, email? ≤160, phone? ≤32, city? ≤80, note? ≤1000 } (email or phone required)
- prayer.request       { request 3-4000 }                                          (always anonymous)
- workforce.volunteer  { full_name 2-120, email? ≤160, phone? ≤32, teams: string[] 0-10 from ALLOWLIST, team_idea? ≤600 } (teams or team_idea required)
ALLOWLIST teams: "Ushering & Hospitality", "Media & Live Stream", "Worship & Music",
"Children's Ministry", "Outreach & Missions", "Prayer Team", "Protocol & Security",
"Sanitation & Facilities", "Follow-up & Counselling", "Administration"
NOT bridged (ever, in v1): teens/youth data, private questions, giving, testimonies, newsletter.

Responses (JSON)
- 202 { "status": "accepted", "receipt": "<uuid>" }     first time, domain row written
- 200 { "status": "duplicate" }                          same (church_id,id), same body hash, already processed
- 409 { "error": "conflict" }                            same id, different body hash (alert)
- 400 / 422 { "error": "<code>" }                        malformed / schema   → website dead-letters
- 401 { "error": "unauthorized" }                        signature/ts/key    → website alerts + backs off
- 413 too large · 429 rate limited (Retry-After s) · 503 bridge disabled · 500 processing failed → website retries
No other success shape is accepted by the website.

SHEP processing rules
- church_id / branch_id come ONLY from the keyId config; branch verified to belong to church at startup.
- One transactional SQL function writes bridge_inbox + domain row; unique source_ref = id on each target table.
- "duplicate" only when inbox row status = processed. Failure → 5xx (never a swallowed 200).
- assigned_to via least-loaded care member; status fixed 'new'; source 'tch_website'; links constant.
- Notification text: plain, truncated, no phone/prayer text on lock screen ("New website prayer request").
- Per-key rate limit + daily cap; over cap → row status 'quarantined', no notifications.
- Possible duplicate (same phone/email + type within 24 h) → flagged, never dropped.
- Inbox payload nulled after processing; consent version + time stored on each row.
- Logs/audit: id, type, status, code only. Never payloads.

## 2. SHEP (or any scheduler) → Website: POST {SITE}/api/bridge/flush
Asks the website to push its pending outbox now. Returns counts only, never data.
- Signed exactly as §1 with path "/api/bridge/flush", host = website host, body "{}",
  using a DIFFERENT secret (website env BRIDGE_FLUSH_KEYS / SHEP env BRIDGE_FLUSH_SECRET).
- Alternatively GET with "Authorization: Bearer <CRON_SECRET>" (Vercel cron / cron-job.org).
- Response 200 { "pending": n, "delivered": n, "dead": n }.
Recommended: SHEP or cron-job.org every 10 min; Vercel daily cron is the backstop.

## 3. Keys
Env on website: SHEP_BRIDGE_URL (https), SHEP_BRIDGE_KEY_ID, SHEP_BRIDGE_SECRET (≥32 random bytes hex),
BRIDGE_ENC_KEY (base64 of 32 random bytes), BRIDGE_ENC_KEY_ID, BRIDGE_FLUSH_KEYS ("id:secret,id:secret"),
CRON_SECRET, BRIDGE_ENABLED (kill switch: "off").
Env on SHEP: BRIDGE_KEYS = JSON [{ "id","secret","church_id","branch_id"|null }], BRIDGE_EXPECTED_HOST,
BRIDGE_ENABLED, BRIDGE_DAILY_CAP, optional BRIDGE_FLUSH_URL/BRIDGE_FLUSH_KEY_ID/BRIDGE_FLUSH_SECRET.
Rotation: add K2 on SHEP → switch website to K2 → wait 48 h → remove K1.
